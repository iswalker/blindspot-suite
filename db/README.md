# Database (Turso)

The dashboard keeps small, durable preferences in a Turso (libSQL) database. Today only **Account Summary
group assignments** are wired up; the rest of the schema is in place so the "YNAB Config" Google Sheet can
be migrated later without reshaping tables.

Everything is optional at runtime: with no database configured the Account Summary tab keeps working from
the browser's localStorage and stays silent.

## Setup

1. Create a database (dashboard at app.turso.tech, or `turso db create blindspot-config`).
2. Get its URL (`libsql://…`) and a token (`turso db tokens create blindspot-config`).
3. Set these as environment variables on **both** hosts, then redeploy:
   - `TURSO_DATABASE_URL` — the `libsql://…` URL (an `https://…` URL works too)
   - `TURSO_AUTH_TOKEN`
   - Vercel: Project → Settings → Environment Variables (Production).
   - Cloudflare Pages: Settings → Variables and Secrets (Production); store the token as a secret.
4. Open the Account Summary tab. The tables are created on first use (`CREATE TABLE IF NOT EXISTS`), and
   the first load copies any assignments already saved in the browser up to the database.

`db/schema.sql` is a readable copy of the schema, generated by `node db/export-schema.js` from
`lib/schema.js` (the source of truth). Applying it by hand is optional.

## YNAB sign-in that lasts (`/api/ynab-auth`)

YNAB access tokens last 2 hours. With `YNAB_CLIENT_SECRET` set, sign-in uses YNAB's authorization-code flow
and the server renews the token for the browser, so you log in about once instead of every couple of hours.

- Set `YNAB_CLIENT_SECRET` (your YNAB OAuth app's client secret) on both hosts, next to the Turso variables
  (Cloudflare: as a secret). `YNAB_CLIENT_ID` is optional; the app's public id is built in.
- The redirect URI registered in the YNAB developer settings must be the site's own URL (what the implicit
  flow already used), e.g. `https://your-site.pages.dev/`.
- The refresh token lives in the `ynab_sessions` table, AES-GCM encrypted with a key derived from the client
  secret; the browser holds only an opaque session id (only its SHA-256 is stored). Changing the client
  secret makes stored tokens unreadable, so everyone simply logs in again.
- Without the secret (or without the database) the app falls back to the old 2-hour implicit flow.

## How requests are scoped (multi-user, no secrets stored)

- The browser sends its YNAB token as `Authorization: Bearer …` to `/api/account-groups`.
- The server asks YNAB `GET /v1/user` who the token belongs to and uses that **YNAB user id** as `user_id`.
  The access token is only forwarded to YNAB, never logged or stored, and only a valid token for that user can
  read or change that user's rows.
- YNAB account and category ids are only unique within a budget, so every row is also keyed by `budget_id`.
- The code talks to Turso over its HTTP API with plain `fetch`, so there is no npm dependency.

## Config rows API

`/api/config` (Vercel `api/config.js`, Cloudflare `functions/api/config.js`, wrappers over `lib/config-rows.js`).

- `GET ?budgetId=[&section=Runway]` → `{ rows: [...] }` in sheet order, every column (all areas when no `section`).
- `PUT { budgetId, section, rows }` replaces one area's rows (used once by the Runway tab's "Move Runway to database" button, which reads the rows from the loaded Google Sheet).
- `PATCH { budgetId, section?, updates?: [{ id, ...fields }], inserts?: [row], deletes?: [id] }` edits, adds and removes rows in one transaction (used by Runway's Edit mode; `section` is required with inserts).

Once an area has rows in the database the app reads that area from there and ignores the sheet's rows for it, so they can be deleted from the sheet.

Areas moved so far, each with its own one-click "move" button and a marker row (`type = Marker`) recording that it
lives in the database:

| Area | Rows | Where |
| --- | --- | --- |
| Runway | every `Runway …` row (section `Runway`) | Runway tab, Edit Text mode |
| Net Worth milestones | `Milestone N` rows (Amount = age, Text = label) + marker `Milestones Migrated` | Net Worth tab, Preview > Milestones |
| Tags & account usage | rows of Type Tag / Account / Category / Category Group (their own Group as section) + marker `Usage Migrated` | Settings > Manage Tags & Account Usage |

`GET /api/config?budgetId=` with no `section` returns every area; the app loads them all once per page load and
caches the last copy in the browser. Usage rows replace the sheet's row for the same Metric + Type (and supply them
outright once deleted from the sheet); account and category pickers store YNAB ids, never shown to the user.

## Account groups API

`/api/account-groups` (Vercel: `api/account-groups.js`, Cloudflare: `functions/api/account-groups.js`, both
thin wrappers over `lib/account-groups.js`).

- `GET ?budgetId=<id>` → `{ groups: { accountId: groupName } }`
- `PUT { budgetId, assignments: [{ accountId, group }] }` → `{ ok: true }`. `group: "Unassigned"` clears the
  assignment. The write is a single transaction.
- Errors: `401` bad/missing YNAB token, `400` invalid input, `503 not_configured` when the env vars are
  missing, `502` when YNAB can't be reached.

If a save fails, the change is kept in localStorage (`acct-summary-pending`) and re-sent on the next load.
